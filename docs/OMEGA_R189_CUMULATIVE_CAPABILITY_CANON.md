# OMEGA R189 — Cumulative Capability Canon

## Purpose

R189 changes the promotion model from revision-centric replacement to cumulative capability preservation.

A newer revision is not allowed to become "the system" by omitting an older admitted organ. The canonical system is the accumulated capability body: the original F00–F23 software families plus all admitted extension organs through R188.

R189 therefore adds a repository-derived non-regression spine without removing or rewriting the existing implementations.

## Core law

```text
CURRENT CANON
  + additive candidate
  + preserved protected artifacts
  + complete predecessor regression suite
  + material measured improvement
  + deployment/live proof
= admissible successor
```

A revision number is provenance, not authority. R188 remains available as a synchronized barrier execution regime, but it does not replace asynchronous, causal-DAG, bounded-wave, or heterogeneous federated execution.

## Why this prevents flattening

Earlier promotion logic could compare capability arrays supplied by a candidate. A caller that forgot to enumerate an old capability could make the comparison incomplete.

R189 instead makes the repository itself part of the proof:

1. A protected artifact inventory is built from the cumulative capability canon.
2. Every protected implementation/test/evidence artifact must exist in the candidate repository.
3. The complete historical regression suite remains part of canonical verification.
4. A candidate may add or strengthen capability but cannot silently delete an admitted organ and still pass.
5. Deprecation is a separate operation and requires migration proof, compatibility route, and rollback.

The artifact guard and historical tests solve different failure modes: the inventory catches structural omission; the existing per-revision tests catch semantic regression.

## Execution regime portfolio

R189 recognizes five coexisting execution regimes:

- `ASYNC_INDEPENDENT` — unrelated work advances concurrently.
- `CAUSAL_DAG` — only real dependencies impose sequence.
- `BOUNDED_WAVE` — large fan-out is capacity-governed.
- `SYNCHRONIZED_BARRIER_R188` — shared logical motion index when the computation truly requires it.
- `HETEROGENEOUS_FEDERATED` — cloud, Genesis, Optical, Sovereign, AI/SAI and other specialized organs keep distinct roles while cooperating.

The selection law is: use the least constraining regime that preserves causal correctness, evidence continuity, load safety and proof.

This prevents synchronization machinery from becoming a bottleneck or overwriting the wider swarm architecture.
